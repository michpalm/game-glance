# Game Glance 3.5.0: stability and polish

Status: release design approved by Michael on 2026-10-22. Controller data, the RetroAchievements provider interface, and measurement-led optimization choices remain investigation work as described below.

## Purpose

Make 3.5.0 a dependable release that users can return to from future versions. Improve responsiveness and small interaction details while preserving the experience established in 3.4.1. Add useful optional integrations without making Home depend on another plugin being present or responsive.

## Confirmed decisions

- Offer every published stable version from 3.5.0 onward, including later minor and major releases, in a version picker. This is not limited to the newest 3.5 patch.
- Include version switching in 3.5.0 itself and retain it in future versions, so returning to 3.5 does not remove the ability to switch again.
- Add Minimal alongside the existing Steam and Spotlight row styles.
- Minimal scrolls like Steam's row. Every game card stays at the small portrait size, including the first and selected cards. Selection never widens a card.

## Proposed delivery order

1. Establish the 3.4.1 baseline on the Ally and Deck; measure Home loading, repeated browsing and page transitions.
2. Implement and verify version switching and settings compatibility.
3. Implement Minimal and check its complete input and transition paths.
4. Make performance and polish changes supported by measurements.
5. Investigate and add controller battery and RetroAchievements support as independently verifiable changes.
6. Run the combined release through device checks, including suspend/resume and plugin reload.

Each piece should be reviewable independently. Additional plugins and status-bar details require specific scope; they are not implicitly included by a general request for polish.

## Version switching

Keep the normal latest-update action. Add an explicit version choice showing the installed version and latest stable release. List installable, published stable releases at or above 3.5.0 in descending version order. Fetch every page needed; a fixed first-page limit would eventually hide 3.5.0.

Use the release's own ZIP URL, version and checksum. Preserve original tags and release assets; corrections ship as new versions. Selecting an older version is a deliberate install action through Decky's confirmation flow. Verify the loader's current upgrade, reinstall and downgrade semantics before choosing the install type; the existing updater always uses its update type.

Cache release metadata with an explicit refresh action. A failed refresh should leave a previously loaded list usable, identify that it could not refresh, and avoid presenting an empty list as if no versions exist. Do not automatically downgrade or select a different version when a requested asset is unavailable.

Before release, test 3.5.0 to a later test version and back, then forward again, on a device. Use test artifacts without publishing invented public releases. Version switching does not guarantee that old code will work indefinitely with future Steam or Decky changes.

### Settings compatibility

Inventory settings and persistent data before changing their formats. Prefer additive changes and preserve unknown settings when saving. Any destructive migration needs a recoverable strategy before it can ship. Test that a round trip through an older version preserves usable settings and that unsupported values fall back safely.

## Minimal row

Persist a third row-style value, `minimal`, and show it in the existing Games row style setting. Keep the current default and the behavior of Steam and Spotlight.

Use the existing small portrait-card dimensions, height and spacing as the starting point. Adapt Steam-style positions and scrolling to remove the first card's extra width. Keep selected-card focus visible without changing layout dimensions. Preserve hero, title and action updates as selection moves.

Check controller steps and held navigation, tap-to-select and tap-to-open, mouse input, drag/flick, collection rows, first/last games, Library entry, loop previews and bounded rendering. The opening transition must start from the actual Minimal layout without a temporary wide card or handover jump. Switching styles must preserve a valid selection and viewport.

## Performance and interaction polish

Existing persistent caches, shared status subscriptions and row rendering limits are the starting point. Measure before extending them. Record cold and warm loading, request counts, row navigation, repeated opens/returns and memory behavior on the target devices. Compare the same games and settings.

Candidates include sharing in-flight requests, preventing repeated reads on every selection, bounding warm-up and background work, and reducing unnecessary renders. Treat each as a candidate until evidence identifies a problem. Cached achievements and playtime must refresh after gameplay; failures must not replace valid data with zero or empty values. Check offline operation, resume and plugin reload as well as the happy path.

Success means a measured improvement or a reproduced interaction defect resolved, with no regression in navigation or data correctness. Do not set an arbitrary numerical performance target before collecting the baseline.

## Controller battery investigation

The shared status store currently reads system battery and network callbacks. Determine what Steam exposes for external controllers on the installed client and devices, including charging, disconnects and unknown levels. Prefer shared subscriptions over per-view polling.

Proposed behavior: show controller battery when reliable information exists; omit an unknown value rather than inventing a percentage. Keep it distinct from the handheld's battery and ensure it fits the narrowest supported layout. Multi-controller presentation and exact placement remain design decisions after inspecting the available data. Do not infer a controller percentage from a coarse level.

## RetroAchievements investigation

First identify the intended Decky plugin and inspect its supported data interfaces and game identification. Determine whether an emulated Steam shortcut can be matched reliably to its achievement set. No integration API or reliable matching is assumed yet.

Proposed initial scope: achievement progress on Home and the game page for reliably matched emulation games, with a useful route to more detail if the plugin supports it. Preserve any meaningful distinction between achievement modes in the source data. Keep Steam achievements unchanged for Steam games.

Reuse the provider's authenticated access where supported rather than introducing another login. Bound requests, cache useful results, refresh after gameplay and handle missing plugins, missing matches, account changes and provider failures without blocking browsing. Never show an unrelated game's achievements based on a title-only guess. Exact UI, provider and refresh behavior must be settled after investigation.

## Verification and release criteria

- Relevant regression tests, the full frontend suite, TypeScript, backend tests for changed backend behavior, and build succeed.
- Ally and Deck checks cover navigation, touch, opening/returning, Minimal, status-bar layout, offline behavior and suspend/resume.
- Version switching is tested in both directions, including returning from 3.5 and preserving settings.
- Plugin integrations are checked both present and absent, including slow/error responses.
- Record measured results separately from planned behavior and previously reported checks.
- Verify release version and packaged contents when packaging is authorized. Publication remains a separate user decision.

## Investigation still needed

- Identify the intended RetroAchievements plugin and establish its usable interface.
- Inspect controller battery data and choose multi-controller presentation.
- Collect baseline measurements to select concrete optimization work.

This draft is a release design, not an implementation plan or evidence that any feature has shipped.
