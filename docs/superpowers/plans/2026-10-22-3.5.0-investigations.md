# 3.5.0 Performance and Integration Investigation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to execute these read-only investigation tasks. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Collect evidence sufficient to choose measurable polish changes and design controller-battery and RetroAchievements support.

**Architecture:** Inspect existing shared stores and provider integrations before adding any data source. These tasks produce measurements and implementation decisions, not speculative product code.

**Tech Stack:** Existing Node CEF probes, Steam client inspection, SSH, repository source and provider documentation.

**Spec:** `docs/superpowers/specs/2026-10-22-3.5.0-stability-design.md`

## Global Constraints

- Do not alter Steam or plugin settings without authorization. Do not clear real user caches just to measure a cold load.
- Treat integration interfaces as unknown until inspected; never guess ROM-to-achievement matches.
- No new credentials, dependency installation, gameplay launch or release publishing is required by these investigations.
- Produce a separate bounded implementation proposal for each validated finding before changing product behavior.

## Review Focus

- Warm runs can hide first-use costs: label cache state and never call unknown cache state cold (Task 1).
- Progress after gameplay can be stale: inspect invalidation and account boundaries (Tasks 1 and 3).
- Controller levels can be coarse: never translate a coarse state into an invented percentage (Task 2).
- Multiple controllers/disconnects: document identity and lifecycle before choosing presentation (Task 2).
- Identical game names can refer to different ROMs/sets: require a reliable mapping (Task 3).
