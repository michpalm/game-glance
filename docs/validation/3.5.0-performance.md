# 3.5.0 performance baseline and candidates

2026-10-22. Baseline code: 8dcc2ac (released 3.4.1). This is a source audit; device timing measurements are pending. Test duration is not UI performance evidence.

## Existing protections verified in source

- `data/cache.ts`: persistent TTLs, including long-lived HLTB matches, background rechecks and cached achievement counts.
- `data/autoPreload.ts`: automatic preloading checks for a running game; do not add another scheduler blindly.
- `home/artShrink.ts`: oversized art is copied at useful display size; existing decode-cost comments describe older measurements, not measurements made in this work.
- `home/useWarmup.ts`: ordered data/art warm-up with cancellation and shared art resolution.
- `home/statusStore.ts`: shared callbacks, equality checks before notifying, and unregister on plugin unload.

## Concrete work in this branch

Minimal does not render wide artwork or hidden blur layers. Version history is loaded on explicit picker opening, shares pending requests, and reuses a fresh complete catalog; it is not fetched on every Home entry. No existing game-data TTL has changed.

## Candidates requiring measurement

1. Minimal still participates in Home's wide-card art warm-up (`home/useWarmup.ts`). Inspect request/decode counts to determine whether disabling that warm-up reduces background work without harming a later style switch or page open.
2. Session maps for artwork, descriptions, HLTB and provider data need a long-session memory/profile check before adding eviction. Entries are not proof of a leak; blob ownership and shared users must be understood before revoking anything.
3. Measure achievement/playtime refresh after gameplay and resume before lengthening any cache lifetime.

## Candidate findings, 2026-10-22 (source)

1. Minimal wide-art warm-up: `useWarmup` runs `warmArt(ids, cardDeps)` for every game in the row, loading and decoding each game's wide card art one at a time. `RecentsRow` is the only consumer of that art, and Minimal never renders a wide card, so in Minimal the whole pass is unused work (about 40 decodes with a 40-game row). Proposed change: skip the wide-card pass while the style is Minimal. A later switch to Steam or Spotlight then loads art on demand, as on a first run. Measure decode time per game before and after on the Ally.
2. Long-session memory: the details memos (achievements, playtime) are already bounded by `DETAILS_MEMO_MAX`. The art paths are not: `HeroBackground` `artMemo`, `logo` `memo`, `cardArt` memo and the `artShrink` copies grow with each distinct game seen, and `artShrink` blob URLs are never revoked. One definite leak: when `loadDecoded(copy)` fails, the blob URL is dropped without `URL.revokeObjectURL`. Revoking that one is safe because nothing else holds it. Evicting the others needs ownership checks first, since several views share the same URL. Measure renderer memory across a long browse session before adding eviction.
3. Refresh after gameplay: achievement and playtime counts update from Steam's `RegisterForAppDetails` pushes (`noteAchievements`, `notePlaytime`), so a refresh depends on that registration still being live when the game ends. Needs a gameplay test: unlock an achievement, return Home and check the chip without a reload.

## Device measurement protocol

Record hardware, Steam and Decky versions, resolution, settings, selected games and cache state. Capture five Home entries, browsing passes and open/return cycles on the same games. Report individual timings and median plus request counts, long tasks and memory when available. A first-observed run is not necessarily a cold run. Do not clear user caches or change settings to manufacture a result.

## Ally observations, 2026-10-22

No timing measurements yet; these are stability observations with the 3.5 development bundle.

- Steam UI hang during code-driven testing: while switching the row style Steam → Spotlight through DOM clicks on the dropdown, with Quick Access closed from code and controller navigation still on the `QuickAccess-NA` tree, Steam's UI stopped responding. Quick Access froze half open. The UI renderer grew from 2.1 GB to 3.1 GB in ten minutes at about 140% CPU, with under 1 GB of RAM left. The style had already saved as `spotlight`. `steam -shutdown` recovered it; the relaunched Steam drew Spotlight normally.
- Reproduction with virtual controller presses only (`FocusNavController.DispatchVirtualButtonClick`), memory sampled every 3 s: Spotlight → Steam → Spotlight with the first card selected, then Steam → Spotlight with Dorfromantik (fifth card) selected. Both closed Quick Access with B and drew Spotlight correctly. Renderer memory stayed at 590–740 MB. Not reproduced.
- Conclusion: most likely caused by the test method, not by 3.5. If a hang appears in normal use, check `RecentsRow` re-rendering when its wide-art choice depends on measured card width.

Deck SSH was unreachable. No UI latency improvement is claimed yet.
