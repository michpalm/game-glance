# Controller battery investigation

2026-10-22: no controller-battery product change yet.

The installed `@decky/ui` 4.12.1 declarations in `dist/globals/steam-client/Input.d.ts` expose `RegisterForControllerBatteryChanges`, `RegisterForControllerListChanges`, `RegisterForActiveControllerChanges` and controller-state callbacks. The battery callback's payload is typed `any`; the declarations do not establish units, charging semantics or supported hardware.

Current Game Glance status reads only system battery and network data through `home/statusStore.ts`, shared across Home/page/screensaver views. An external-controller adapter belongs at that shared boundary.

## Ally inspection, 2026-10-22

Read-only, through the approved CEF tunnel. Identifiers (serials, chip IDs, unique IDs, MAC addresses) were left out of every sample.

- The declared callbacks do not exist in this Steam client: `SteamClient.Input` has no `RegisterForControllerBatteryChanges` and no `RegisterForControllerListChanges`. The `@decky/ui` declarations are out of date, so an adapter must not depend on them.
- Steam's own source is `window.ControllerStore`, a MobX store. `m_controllerList` holds one entry per controller, and each entry carries `ucBatteryLevel` and `bCharging` next to `strName`, `eControllerType`, `bWireless`, `bBluetooth` and `nControllerIndex`. Steam updates it through its own `fnOnControllerBatteryState` handler, and `m_controllerBatteryNotifications` backs Steam's low-battery notices.
- Sample with two controllers connected:

| Controller | Type | Connection | ucBatteryLevel | bCharging |
| --- | --- | --- | --- | --- |
| Asus Rog Ally Controller (built-in) | 120 | wired, not Bluetooth | 100 | false |
| 8BitDo Ultimate 2C Wireless | 30 | Bluetooth | 100 | false |

- The built-in controller reports 100 and not charging while the Ally itself was charging, so its value is a placeholder, not a battery. Show only external controllers (Bluetooth or wireless); the system battery already covers the handheld.

### Three sources compared, same moment

Steam's Bluetooth settings in Quick Access show 18% for this controller (confirmed by the user on the Ally). For the 8BitDo Ultimate 2C over Bluetooth:

| Source | Reading |
| --- | --- |
| Steam `ControllerStore.m_controllerList[].ucBatteryLevel` | 100, not charging |
| BlueZ `org.bluez.Battery1` (`bluetoothctl info`, "Battery Percentage") | 18 |
| UPower HID battery device for the controller | 0% |

`ucBatteryLevel` is not this controller's battery: it stays at 100, the same placeholder the built-in controller reports. UPower's HID reading is also empty. BlueZ's Battery1 value matches Steam's Bluetooth settings: it is the correct source.

Consequence for the design: the Steam frontend has no Bluetooth battery API (`SteamClient` has no Bluetooth functions), so the frontend cannot read it. Game Glance would need its Python backend to read `org.bluez.Battery1.Percentage` over D-Bus for connected devices, and pass name, percentage and connection to the shared status store. Devices without Battery1 show nothing.

### Still unknown

- Whether BlueZ's percentage moves in single percent or coarse steps; charging is not part of Battery1.
- Wired (USB) controllers, which BlueZ does not see.
- Disconnect/reconnect and resume behaviour.

Need sanitized samples for controller identity, initial state and changes, percentages versus coarse levels, charging, disconnect/reconnect, active controller and resume. Do not expose controller serial numbers or invent percentage values from coarse levels.

Proposed UI remains conditional on that evidence: a distinct controller indicator when reliable data exists; no unknown placeholder percentage. Multiple-controller display needs a decision based on actual data and the available space.

## Device check, 2026-10-22 (Ally)

Not tested: two or more controllers (only one available), resume from sleep, and whether reading continues behind a running game.

### Read on change, 2026-10-22

After a reboot the controller connected 30 s after the first read and took up to a minute to appear. Probe of Steam's controller callbacks while turning the 8BitDo off and on: only `SteamClient.Input.RegisterForUnboundControllerListChanges` fires on disconnect and reconnect (about 0.2 s before `ControllerStore` updates; twice on reconnect; once on registering). `RegisterForActiveControllerChanges` fired only on registering. The store now reads 2 s after that callback (debounced; the registration call ignored), with the 60 s read kept as a fallback. On the Ally: off → item gone within about 2 s; reconnect at 23:31:39 → item back at 23:31:41.
